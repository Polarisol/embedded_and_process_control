# בוחן מכונות מצבים

ענו על כל השאלות, ואז לחצו על **הגשת התשובות** כדי לראות את הציון ואת התיקונים.

## מערכת מתוארת בעזרת מכונת מצבים. מה נכון לגביה בכל רגע?
- [ ] היא יכולה להיות בכמה מצבים בבת אחת, כל עוד הם לא סותרים זה את זה
  > מכונת מצבים אף פעם לא מערבבת מצבים. רמזור לא יכול להיות "קצת אדום וקצת ירוק".
- [x] היא נמצאת בדיוק במצב אחד
  > נכון. המערכת תמיד נמצאת בדיוק באחד מהמצבים שלה, והיא יודעת מה בא אחר כך.
- [ ] היא לא נמצאת באף מצב עד שקורה אירוע
  > תמיד יש מצב נוכחי. כשמדליקים את המכשיר הוא נמצא במצב **ההתחלה**.
- [ ] היא עוברת למצב הבא בכל סיבוב של `loop()`
  > המצב משתנה רק כשאירוע מעביר אותו לאורך חץ. בלי אירוע הוא נשאר במקום.
> מכונת מצבים היא רשימה של **מצבים**, **אירועים** ו**מעברים**. המערכת תמיד נמצאת בדיוק במצב אחד, ואירוע יכול להעביר אותה למצב אחר.

## למנורה יש שני מצבים, OFF ו-ON, וכפתור אחד. מה עושה לחיצה על הכפתור?
- [ ] היא תמיד מדליקה את המנורה
  > זה נכון רק במצב OFF. במצב ON אותה לחיצה מכבה את המנורה.
- [ ] היא תמיד מכבה את המנורה
  > זה נכון רק במצב ON. במצב OFF אותה לחיצה מדליקה את המנורה.
- [ ] כלום, כי כפתור הוא לא אירוע
  > לחיצה על כפתור היא אירוע קלאסי, בדיוק כמו קריאה של חיישן או טיימר שהזמן שלו נגמר.
- [x] זה תלוי במצב הנוכחי
  > נכון. במצב OFF הלחיצה מדליקה את המנורה, ובמצב ON היא מכבה אותה. צריך לדעת את המצב כדי לדעת מה אירוע יעשה.
> זה הלב של כל מכונת מצבים: אותו אירוע יכול לעשות דברים שונים, ו**המצב הנוכחי** קובע מה.

## בדיאגרמת מצבים, מה הכיתוב שעל חץ?
- [x] האירוע שגורם למעבר לקרות
  > נכון. למשל "button pressed" או "after 30 s".
- [ ] השם של המצב שהחץ מצביע עליו
  > שם המצב כתוב בתוך העיגול או המלבן שלו, לא על החץ.
- [ ] מה המנועים והנורות עושים במצב הזה
  > היציאות של מצב כתובות בתוך המצב, לא על החיצים.
- [ ] מצב ההתחלה
  > את מצב ההתחלה מסמן חץ שיוצא מנקודה קטנה, ואין עליו כיתוב של אירוע.
> בדיאגרמת מצבים יש ארבעה חלקים: **מצבים** (עיגולים), **מעברים** (חיצים), **אירועים** (הכיתוב על החיצים) וחץ **התחלה** שיוצא מנקודה קטנה.

## דלת אוטומטית נמצאת במצב CLOSING (נסגרת) כשאדם נכנס. לפי דיאגרמת המצבים של הדלת, מה צריך לקרות?
- [ ] כלום. הדלת מסיימת להיסגר ואז נפתחת שוב
  > אז הדלת תפגע באדם. זו בדיוק הבעיה שהדיאגרמה עוזרת לנו לתפוס.
- [ ] הדלת עוברת ישר ל-OPEN
  > הדלת סגורה חלקית, אז היא לא יכולה להיות פתוחה לגמרי בבת אחת. המנוע צריך קודם להסתובב קדימה.
- [x] הדלת חוזרת ל-OPENING (נפתחת)
  > נכון. החץ האדום יוצא מ-CLOSING וחוזר ל-OPENING כשמזוהה אדם.
- [ ] הדלת עוצרת ונשארת במקום לתמיד
  > אין בדיאגרמה מצב "תקועה". הדלת חייבת להיפתח שוב כדי לתת לאדם לעבור.
> כשמתכננים מכונת מצבים, עוברים על **כל מצב** ושואלים "מה אם האירוע הזה קורה **עכשיו**?". כך מוצאים מקרים כמו דלת שנסגרת על מישהו, לפני שהם מגיעים למכשיר האמיתי.

## במכונת המצבים הזו של ארדואינו, איזו שורה היא **מעבר**?
```c
switch (state) {
  case LAMP_OFF:
    digitalWrite(LED_PIN, LOW);
    if (pressed) {
      state = LAMP_ON;
    }
    break;
  // ...
}
```
- [ ] `switch (state) {`
  > השורה הזו בוחרת איזה קוד של איזה מצב להריץ. היא לא מעבירה את המכונה לשום מקום.
- [ ] `digitalWrite(LED_PIN, LOW);`
  > זו **היציאה** של מצב OFF: מה הנורה עושה בזמן שאנחנו בו.
- [ ] `case LAMP_OFF:`
  > כל `case` מתאים ל**מצב** אחד (עיגול אחד בדיאגרמה), לא לחץ.
- [x] `state = LAMP_ON;`
  > נכון. שינוי משתנה המצב הוא המעבר, החץ מ-OFF ל-ON.
> כל **מצב** הופך ל-`case`, **היציאות** שלו הן הקוד שבתוכו, כל **אירוע** הוא `if`, וכל **מעבר** הוא שינוי של המשתנה `state`.

## מה משתבש בקוד הזה כשהמנורה במצב `LAMP_OFF`?
```c
switch (state) {
  case LAMP_OFF:
    digitalWrite(LED_PIN, LOW);
    if (pressed) {
      state = LAMP_ON;
    }
  case LAMP_ON:
    digitalWrite(LED_PIN, HIGH);
    if (pressed) {
      state = LAMP_OFF;
    }
    break;
}
```
- [ ] הקומפיילר מסרב לקמפל אותו
  > הוא מתקמפל בלי שום שגיאה. זה מה שהופך את הטעות הזו לערמומית.
- [x] הקוד ממשיך לרוץ לתוך ה-`case` של `LAMP_ON`, ולכן הנורה נדלקת גם במצב OFF
  > נכון. בלי `break`, שפת C ממשיכה לתוך ה-`case` הבא, וסיבוב אחד עושה את העבודה של שני מצבים.
- [ ] רק ה-`case` של `LAMP_OFF` רץ, ולכן הכול עובד כמו שצריך
  > שפת C עוצרת רק ב-`break` (או בסוף ה-`switch`). כאן ב-`case` של `LAMP_OFF` אין `break`.
- [ ] התוכנית קופצת חזרה לתחילת `loop()` ומדלגת על ה-`case` של `LAMP_ON`
  > הגעה לתווית `case` הבאה לא עוצרת שום דבר. הקוד ממשיך לרוץ ישר דרכה.
> סיימו כל `case` ב-`break;`. בלעדיו התוכנית "נופלת" לתוך הקוד של המצב הבא.

## רמזור מחכה במצב GREEN בעזרת `delay(4000)`. הולך רגל לוחץ על הכפתור שנייה אחת אחרי תחילת ההמתנה. מה קורה?
- [ ] הרמזור עובר מיד לצהוב
  > בזמן `delay()` הלוח לא עושה כלום, אז הוא לא יכול להגיב ללחיצה.
- [ ] הלוח עוצר את ההמתנה מוקדם ומטפל בלחיצה
  > הקוד שלכם לא יכול לקטוע את `delay()`. היא פשוט מחכה עד שהזמן נגמר.
- [x] הלוח לא שם לב ללחיצה, כי הוא עסוק בהמתנה
  > נכון. בזמן ש-`delay()` רצה הלוח לא קורא כפתורים או חיישנים, ולכן לחיצה קצרה הולכת לאיבוד.
> אל תשתמשו ב-`delay()` במכונת מצבים. במקום זה, שמרו בעזרת `millis()` את הזמן שבו נכנסתם למצב, ובדקו בכל סיבוב כמה זמן אתם בו. כך הלוח ממשיך להקשיב לכל השאר.

## בקוד של הרמזור, כל מעבר עובר דרך `goTo()`. למה?
```c
void goTo(LightState next) {
  state = next;
  enteredAt = millis();
}
```
- [ ] כי C לא מרשה לשנות את `state` ישירות
  > מותר לשנות את `state` ישירות. `goTo()` נמצאת שם כדי שלעולם לא תשכחו את השורה השנייה.
- [ ] כדי שהלוח יחכה לפני שהוא נכנס למצב הבא
  > `goTo()` לא מחכה בכלל. היא חוזרת מיד.
- [x] כדי שהטיימר יתאפס בכל פעם שהמצב משתנה
  > נכון. `enteredAt` מקבל את הזמן הנוכחי, ולכן המצב החדש מתחיל לספור מאפס.
- [ ] כדי להדפיס את שם המצב החדש ל-Serial Monitor
  > אין כאן `Serial`. הפונקציה משנה את המצב ושומרת את הזמן.
> אם משנים את `state` בלי לאפס את הטיימר, המצב הבא חושב שהזמן שלו כבר נגמר. שינוי מצב דרך פונקציה אחת, כמו `goTo()`, הופך את הטעות הזו לבלתי אפשרית.

## אילו מהקריאות האלה שייכות ל**תחילת** `loop()`, לפני ה-`switch`? בחרו את כל התשובות הנכונות.
- [x] `digitalRead(BUTTON_PIN)`
  > כן. היא חוזרת מיד, ולכן לקרוא אותה בתחילת הלולאה כמעט לא עולה כלום.
- [ ] `pulseIn(ECHO_PIN, HIGH, 30000)`
  > לא. `pulseIn()` מחכה להד, ולכן היא נכנסת ל-`case` של המצב היחיד שצריך אותה.
- [x] `millis() - enteredAt`
  > כן. בדיקת הזמן חוזרת מיד.
- [x] `buttonPressed()`
  > כן. היא קוראת את הכפתור וחוזרת מיד, כך שהתוצאה מוכנה לכל מצב שצריך אותה.
> קריאות ש**חוזרות מיד** נכנסות לתחילת `loop()`, פעם אחת בכל סיבוב. קריאות ש**מחכות**, כמו `pulseIn()` או המתנה להודעה ב-`Serial`, נכנסות ל-`case` שצריך אותן, כדי שלא יאטו את כל שאר המצבים.
